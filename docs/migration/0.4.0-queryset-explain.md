# 0.4.0 QuerySet Plan Diagnostics

Reinhardt 0.4.0 adds a backend-aware, plan-only `QuerySet::explain` operation.
It compiles the same filtered, joined, ordered, and limited typed SELECT used by
normal QuerySet evaluation, then wraps that statement in a backend-specific
EXPLAIN command.

## Typed usage

Generated model fields remain the preferred way to construct the inspected
query:

```rust
use reinhardt_db::orm::{ExplainBody, ExplainFormat, ExplainOptions};

let output = Account::objects()
    .filter(Account::field_status().eq(AccountStatus::Active))
    .filter(Account::rel_owner().into_typed().field_email().eq("ada@example.com"))
    .order_by(Account::field_created_at().desc())
    .explain(ExplainOptions::default().format(ExplainFormat::Json))
    .await?;

if let ExplainBody::Json(plan) = output.body {
    inspect_plan(plan);
}
```

`ExplainOutput` includes the backend, the effective `ExplainFormat`, and an
`ExplainBody`. JSON plans are decoded into `serde_json::Value`, single-column
text plans are joined with newlines, and tabular backend plans are retained as
JSON row objects. Plan rows never pass through model deserialization.

## Caller-owned executors

Use `explain_with_db` when the equivalent QuerySet execution uses a caller-owned
ORM connection. Use `explain_with_executor` inside an active transaction so the
plan is generated on the transaction's dedicated connection:

```rust
let output = connection.atomic(async |transaction| {
    Account::objects()
        .filter(Account::field_id().eq(account_id))
        .explain_with_executor(transaction, ExplainOptions::default())
        .await
        .map_err(reinhardt_core::exception::Error::from)
}).await?;
```

## Backend capabilities

| Backend | Supported formats | Supported options |
|---------|-------------------|-------------------|
| PostgreSQL | `Text`, `Json`, `Xml`, `Yaml` | `verbose`, `costs`, `settings` |
| MySQL | `Text`, `Json` | none |
| SQLite | `Text` | none |
| CockroachDB | `Text` | none |

`Text` maps to MySQL/MariaDB's traditional output and to `EXPLAIN QUERY PLAN`
on SQLite. Unsupported formats or options return an `Unsupported` database
error before any executor method is called. QuerySets with CTEs, lateral joins,
or a subquery source are rejected for every backend before the SELECT is
compiled.

Because the MySQL optimizer can evaluate scalar subqueries and expressions while preparing ordinary
`EXPLAIN` output, Reinhardt conservatively rejects MySQL plans containing
subqueries, CTEs, unions, functions, or unchecked expressions before calling
the executor. Plain typed filters, relation joins, ordering, and limits remain
available. SQLite documents its plan rows as diagnostic output whose exact
fields can change between releases; consume `ExplainBody::Rows` for inspection,
not as a stable persistence format.

## Safety boundary

Reinhardt's API is intentionally stricter than Django's string-oriented
EXPLAIN options. There is no representation for `ANALYZE`, arbitrary option
strings, buffer or timing statistics, or other data-executing options. The
executor receives one EXPLAIN statement containing the compiled SELECT; it
never receives the original SELECT as a separate query.
