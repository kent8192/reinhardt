# Typed manager upserts in 0.4.0

Reinhardt 0.4.0 replaces the string-keyed manager `get_or_create` API with
typed `get_or_create` and `update_or_create` builders. Generated model field
accessors now carry both the model and field value type, so a field from the
wrong model or a value of the wrong type fails during compilation.

Generated field accessors are required for typed upsert builders. The safe
manual `FieldRef::new` constructor remains available for lower-level dynamic
filtering, but it produces an unverified field reference and cannot be passed
to `get_or_create` or `update_or_create`. Replace manually constructed upsert
references with the accessor generated for the model:

```rust,ignore
// Lower-level dynamic filtering can continue to use:
let slug = FieldRef::<Tag, String>::new("slug");

// Typed upserts require:
let slug = Tag::field_slug();
```

Generated `field_*()` accessors are the required upsert construction path because
they bind the logical field name, physical column name, model, and value type
from the same model metadata.

## Migrate `get_or_create`

The removed API accepted string-keyed maps:

```rust,ignore
use std::collections::HashMap;

let lookup = HashMap::from([("slug".to_owned(), "rust".to_owned())]);
let defaults = HashMap::from([("display_order".to_owned(), "10".to_owned())]);
let (tag, created) = Tag::objects()
    .get_or_create(lookup, Some(defaults))
    .await?;
```

Replace it with generated field accessors and typed values:

```rust,ignore
let (tag, created) = Tag::objects()
    .get_or_create()
    .lookup(Tag::field_slug(), "rust")
    .default(Tag::field_display_order(), 10_i32)
    .execute()
    .await?;
```

`default` values are used only when this invocation creates the row. The
returned `created` flag is `true` only when this invocation inserted it. If a
concurrent insert wins the race, Reinhardt reloads the winner and returns
`created == false`.

The builder's `execute_with` method accepts a `DatabaseConnection` or an
`AtomicTransaction` created by `DatabaseConnection::atomic_write`. This keeps
the lookup and insert-race recovery on a connection that can safely retry it:

```rust,ignore
let (tag, created) = connection
    .atomic_write(async |transaction| {
        Tag::objects()
            .get_or_create()
            .lookup(Tag::field_slug(), "rust")
            .default(Tag::field_display_order(), 10_i32)
            .execute_with(transaction)
            .await
    })
    .await?;
```

The old `get_or_create_with_conn`, `get_or_create_queries`, and
`get_or_create_sql` methods are removed. Use the builder's `execute_with`
method for caller-owned execution. Use `reinhardt-query` directly when an
application needs to construct or inspect lower-level SQL statements.

## Use `update_or_create`

The typed update/create builder uses `set` values on both branches and
`create_default` values only on the create branch:

```rust,ignore
let (profile, created) = Profile::objects()
    .update_or_create()
    .lookup(Profile::field_user_id(), user.id)
    .set(Profile::field_last_seen(), now)
    .create_default(Profile::field_created_at(), now)
    .execute()
    .await?;
```

When an existing row matches, Reinhardt locks it and applies `set` values.
When no row matches, the insert combines lookup, `set`, and `create_default`
values. If another transaction wins the insert race, Reinhardt locks that
winner, applies the requested update, and returns `created == false`.

`execute` owns the write-intent transaction. Caller-owned execution is
deliberately narrower than get/create: `execute_with` requires an
`AtomicTransaction` created by `DatabaseConnection::atomic_write`.

```rust,ignore
let (profile, created) = connection
    .atomic_write(async |transaction| {
        Profile::objects()
            .update_or_create()
            .lookup(Profile::field_user_id(), user.id)
            .set(Profile::field_last_seen(), now)
            .create_default(Profile::field_created_at(), now)
            .execute_with(transaction)
            .await
    })
    .await?;
```

An `AtomicTransaction` from ordinary `DatabaseConnection::atomic` is rejected
before any upsert SQL is issued. On SQLite, `atomic_write` issues
`BEGIN IMMEDIATE` before the first lookup so writers are serialized before
reading. On MySQL it starts the transaction at `READ COMMITTED`, avoiding
InnoDB missing-row next-key gap-lock deadlocks while the unique constraint
still serializes competing inserts.

## Lookup and assignment rules

Every upsert lookup must cover at least one supported immediate uniqueness
guarantee:

- the complete primary key;
- a field declared with `unique = true`; or
- every field in an immediate, unconditional unique constraint.

Conditional and deferrable unique constraints do not prove an upsert lookup.
A nullable unique lookup is accepted only when its metadata guarantees that
nulls are not distinct. Extra lookup fields are allowed, but the full lookup
must still match at most one row.

Each field may appear only once in a builder role. A lookup field cannot also
appear in `default`, `set`, or `create_default`; changing the identity used to
find the row is rejected. Generated, non-editable, unknown, and
relation-traversal fields are also rejected before database access.

The high-level builders intentionally do not accept dynamic string field
names. Validate dynamic names and values against `Model::field_metadata()`,
then use an explicitly lower-level `QuerySet`/`Filter` or `reinhardt-query`
surface. Do not use the unverified `FieldRef::new` result for typed upserts or
construct unchecked identifiers from untrusted input.

## Custom manager upsert hooks

`CustomManager::before_upsert_write` is distinct from `before_save`. It
receives typed pending values for the create branch and a mutable loaded model
for the update branch:

```rust,ignore
use reinhardt_core::exception::Result;
use reinhardt_db::orm::upsert::UpsertWrite;

fn before_upsert_write(
    &self,
    write: &mut UpsertWrite<'_, Account>,
) -> Result<()> {
    match write {
        UpsertWrite::Create(create) => {
            create.set(Account::field_normalized_name(), "normalized")?;
        }
        UpsertWrite::Update(account) => {
            account.normalized_name.make_ascii_lowercase();
        }
    }
    Ok(())
}
```

`UpsertCreate::get` returns `None` when a value is absent from the pending
lookup and create assignments. This includes fields that the database would
fill from a default; the hook runs before the insert and does not query that
default. `UpsertCreate::set` cannot replace lookup fields and validates
writability before SQL execution.

Lookup-field immutability applies to the create view only.
`UpsertWrite::Update(&mut M)` is a normal mutable model and may change any
writable field, including a field used by the lookup. Reinhardt persists those
changes with a predicate built from the locked model's old primary key, so
changing a lookup field or even the primary key does not change which locked
row is updated.

Hooks may run for an insert attempt that later loses a concurrent race, and a
successful hook may still be followed by transaction rollback. External side
effects from this hook are therefore unsupported. Keep the hook limited to
deterministic model/value mutation and validation that can safely be repeated
or discarded.
